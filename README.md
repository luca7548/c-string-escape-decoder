# C String Escape Decoder

Decodes the escape sequences that appear inside C/C++ string literals — simple escapes like `\\n`, hex escapes like `\\x41`, and octal escapes like `\\101` — into the characters they represent.

```python
from c_string_escape_decoder import decode

decode(r"hello\nworld\x41\101")  # -> 'hello\nworldAA'
```

The only name exported is `decode`, which takes a `str` and returns a `str`.

## Why this exists

When you read C source text in Python — a config file generated by a C program, a header of string constants, a probe of compiler output — the text still carries its escapes. Writing this by hand is fiddly because the octal rule is up-to-three-digits and greedy, and hex is up-to-N-digits in the standard. This library does the greedy-but-bounded parse so callers do not have to.

The deliberate scope choice: hex escapes are required to be exactly two digits (`\\xHH`). The C standard permits an unbounded run of hex digits, which makes parsing greedy in ways that are rarely what you want and easy to get wrong. Fixing the length at two keeps the grammar local and unambiguous. Octal escapes are the standard one-to-three-digit greedy form, because that is the form actually used in real C source.

## The awkward edge

A backslash followed by a character the standard does not define as an escape (for example `\\g`) is emitted literally, backslash included. This mirrors how most C compilers behave: warn, but keep the text. If you need strict rejection of unknown escapes, check the output for a surviving backslash.

Incomplete hex escapes (`\\x1` without a second digit) are likewise left untouched rather than padded or rejected.

## Performance

The window keeps a bounded buffer, so `push` is constant time and memory does not
grow with the length of the stream. `peak` and `trough` are linear in the window
size, which is the trade that keeps `push` cheap.
